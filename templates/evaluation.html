📐 5. Scalability Analysis
Horizontal, vertical, CI/CD automation & state architectural considerations
⬆ Vertical Scaling
Mechanism: Increasing instance resources (CPU cores and RAM) on Render (upgrading from Free/Starter 512MB RAM to Standard/Pro tiers with 4GB+ RAM and dedicated vCPUs).

Impact: Accommodates heavier in-memory buffers, faster request handling, and prevents Out-Of-Memory (OOM) termination under high concurrent request volume.
➡ Horizontal Scaling
Mechanism: Running multiple Gunicorn process workers (gunicorn -w 4 app:app) and spinning up multiple container replicas behind Render's load balancer.

Impact: Distributes inbound HTTP traffic across independent worker processes, maximizing multicore utilization and providing fault isolation.
🔄 Auto-Deploy & CI/CD
Mechanism: Render's automated deployment hook triggers immediately on git push to the default branch.

Workflow: GitHub Actions executes linting and pytest test suites. Upon successful build, Render pulls the commit, installs dependencies from requirements.txt, and launches the web service with zero-downtime rolling replacement.
💡 Limitations & Production Recommendation
Limitation: In-memory metrics do not persist across instance restarts and cannot aggregate across multiple horizontally scaled instances (each instance maintains its own memory isolated counters).

Production Recommendation: In enterprise production environments, use a centralized datastore such as Redis for distributed atomic metric increments or export Prometheus-compatible metrics to TimescaleDB / Grafana.

Free Tier Constraints & Operational Considerations:
  • Monthly Hours: 750 hours/month shared pool across web services on Render free tier.
  • Cold Starts: Web services automatically spin down after 15 minutes of inactivity; the initial wakeup request experiences ~30–50 seconds latency while the container boots.
  • Resource Caps: 512 MB RAM limit and shared vCPU. In-memory data structures must be constrained to prevent memory exhaustion.
